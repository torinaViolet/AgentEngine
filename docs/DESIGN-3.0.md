# AgentEngine 3.0 设计讨论记录

记录日期：2026-10-08。

本文保存从 2.2.0 开始的 3.0 重构讨论、接口草案和方案演进。运行时代码现已切换到 3.0.0；历史草案不作为最终 API，请阅读 [当前 API](./API.md)、[实施状态](./PLAN-3.0.md) 与 [迁移说明](./MIGRATION-3.0.md)。文中的旧实现分析对应重构前版本。

2026-10-08：用户认可当前设计方向，剩余常规细节按实际业务需要收敛。[设计基线与实施计划](./PLAN-3.0.md) 记录后续采用的默认选择与阶段目标。本讨论记录保留方案演进，不将历史草案当作最终接口。

## 1. 重构目标

将 AgentEngine 设计成结构清晰、模块解耦、API 易懂且容易发现的 Agent 框架。

本次按 3.0 大版本设计，重点重新审视职责和接口，不以维持所有 2.x 接口为前提。实施采用新根入口与显式 legacy 兼容层。

主要动机：

- 逐渐脱离模型厂商 SDK，实现框架自己的平台请求和协议转换。
- 拆开 Message 与 Session，解决消息内容和会话组织职责混杂的问题。
- 整理配置入口、配置归属、默认值和覆盖规则，减少需要记忆的隐式行为。
- 明确 Agent 的执行循环、工具审批、继续生成和会话维护方式。
- 保留模块独立使用的能力，允许业务直接操作会话和构建上下文。

## 2. 已确认的设计方向

### 2.1 Message 独立于会话节点

Message 成为独立的消息数据模型，表达角色、内容及必要的消息属性。

父子关系、节点位置、候选选择和轮次归属由 Session 负责。Message 不再承担树节点职责，现有 `parent`、`children`、`append()`、节点删除和历史查询等会话能力需要迁出。

2026-10-08 补充确认：内容编辑保留在 Message 中，由最了解内容结构的 Message 实现。Session 提供详细查询让用户获得具体 Message，并可提供委托 Message 编辑方法的便捷入口。Message 不承担会话结构修改、业务保存或界面渲染。

倾向使用带编辑能力的 Message 对象；编辑方法、只读视图、标识和版本的具体实现仍需确定。

### 2.2 提供三种会话模型

| 会话类型 | 组织方式 | 主要用途 |
| --- | --- | --- |
| TreeSession | 标准树结构，节点引用消息 | 对话分支、回退、旧消息编辑后的分支生成 |
| ListSession | 有序槽位，每个槽位包含多个候选和当前选中项 | 可切换候选的列表式会话 |
| AgentSession | 按用户交互轮次组织消息，轮内允许多个模型步骤 | Agent 交互与执行过程管理 |

这些会话可独立创建和使用。共同操作接口及各自特有 API 待定义，不要求所有会话都暴露树形光标或相同的结构操作。

### 2.3 ListSession 的候选单位可配置

默认候选单位为 `sequence`，一个候选是一段有序消息序列。

普通回复可以只有一条消息；工具调用回复可以包含完整的 `Assistant → Tool → Assistant` 轨迹。切换候选时切换完整序列，不能只替换最终文本而遗留另一候选的工具轨迹。

另一个候选单位为 `turn`，一个候选是一整轮用户交互，包含输入和该轮内的模型步骤、工具结果与回复。

消息序列模式示例：

```text
槽位 1：用户输入
槽位 2：回复候选 A / 回复候选 B
        每个候选都可以包含多条消息
槽位 3：下一条用户输入
```

交互轮模式示例：

```text
槽位 1：交互候选 A / 交互候选 B
        每个候选都包含输入与完整生成过程
槽位 2：下一轮交互的候选
```

切换早期候选后，后续历史是否保留、如何标记失效、怎样接受或重新生成，仍需明确。候选切换不意味着撤销工具已经产生的外部副作用。

### 2.4 AgentSession 的一轮是一次用户交互

一轮交互可以包含多次模型调用及工具执行：

```text
第 1 轮
  用户输入
  模型步骤 1：助手发起工具调用，工具返回结果
  模型步骤 2：助手再次调用工具，工具返回结果
  模型步骤 3：助手给出最终回复

第 2 轮
  用户补充输入
  模型步骤 1：助手给出回复
```

不能把“一轮用户交互”与“一次模型调用”混为一谈。

### 2.5 框架自行实现 Provider

自行实现 OpenAI、Gemini 和 Anthropic 的接口接入，包括请求发送、响应读取和统一数据转换，逐步脱离厂商 SDK。

用户使用统一的 Message、工具定义和常用请求配置。提交请求时，转换器将统一结构转换为平台格式；接收响应时，再转换为统一响应和增量事件。

转换范围需要覆盖消息、工具、配置、完整响应与流式事件。不能只处理消息数组而把其余平台格式交给用户。

SDK 接入是否保留为可选适配方式、协议级 Provider 的名称和数量，待确定。

### 2.6 工具审批归入工具执行模块

工具审批与工具执行形成可独立使用的能力，避免审批仅存在于 Agent 内部。

Agent 负责协调对话流程和运行状态，调用工具执行入口并反映审批等待及执行结果。工具执行模块内部的授权策略、人工审批入口、超时和错误语义还需要设计。

### 2.7 Agent 提供便捷功能，并维护传入的独立模块

用户可以独立创建 Session 和 PromptBuilder，直接编辑会话、调整上下文规则，再交给 Agent 使用。

Agent 使用传入的实例，根据该 Session 的组织规则自动维护会话。用户通过 Agent 获取到的应当是同一个实例，不另行维护隐藏的会话副本。

- 传入 Session：使用该实例，无需再指定会话模式。
- 未传入 Session：需要指定 Agent 模式，由模式决定自动创建 TreeSession、ListSession 或 AgentSession。
- 未传入 PromptBuilder：Agent 自动创建一个可获取、可操作的默认实例。
- 自动创建或外部传入的 Session、PromptBuilder，都可以通过 Agent 获取。

模式字段主要用于自动创建 Session；具体参数名、模式与 Session 配置的类型约束待确定。

### 2.8 对话入口与继续生成

对话入口倾向使用易懂的 `chat()` 名称，开始新交互并自动维护 Session。

“继续生成”的目标行为已经明确：

1. 从待继续的助手消息取得已有思考和回答。
2. 将已有思考作为助手消息回传，并提供已有回答所需的上下文。
3. 接上用于继续生成的用户指令，再请求模型。
4. 将新思考拼接到原思考，将新回答拼接到原回答。
5. 最终会话不保留继续指令，不产生额外的普通用户交互。

```text
原回复：thinking = A，text = B
新生成：thinking = C，text = D
合并后：thinking = A + C，text = B + D
```

平台协议所需的原生状态也需要保留。具体回传格式由 Provider 转换层处理。

继续过程中有工具调用、部分生成失败、用户同时编辑目标消息等情况，尚需定义提交和合并规则。

### 2.9 所有 Session 保留轮次与工具执行信息

TreeSession、ListSession、AgentSession 均需要保留消息轮次和工具使用轮次信息。AgentSession 的区别是以交互轮组织会话，不能将轮次记录能力限定在该类型中。

具体 Turn、Run、Step、工具执行记录及其与 Message 的关系见 [消息、会话与运行记录契约草案](./DATA-MODEL-3.0.md)。仅在 Agent 的运行状态或流式事件中记录，不足以支持会话保存、恢复和后续查询。

### 2.10 保存、显示与模型上下文允许不同

模型生成内容、Session 中保存的内容、界面显示和下一次请求的上下文不保证一致。框架提供清楚的转换与关联入口，允许业务实现提交前处理、临时上下文转换和显示投影。

Message 负责当前消息内容；Session 负责组织与查询；业务控制显示和实际持久化方式。如何记录生成来源、如何通知提交结果等具体契约仍为设计草案。

## 3. 当前 2.2.0 实现备忘

本节记录讨论时对源码的核对结果，用于区分现状与 3.0 目标。后续实现变化后应同步更新或归档本节。

### 3.1 当前 Agent 的执行循环

主要代码见 [Agent.ts](../src/legacy/agent/Agent.ts)。

```text
run(content)
  → 创建用户 Message
  → runWith(message)：追加到 Session
  → 开始执行，调用 Session.beginGeneration()（若有）
  → 每次模型调用：
      Session.history()
      → PromptBuilder.build()（若提供）
      → 清理空消息
      → Adapter 构建平台请求
      → Client 请求模型
      → Parser 解析流，或 Adapter 解析完整响应
      → 等待 BEFORE_ASSISTANT_COMMIT
      → Session.addAssistant()
      → 如有工具调用且配置了 ToolKit：审批、执行、写入工具结果
      → 再次请求模型
  → 结束，调用 Session.endGeneration()（若有），清理资源
```

- `generate()` 使用已有会话上下文，不追加用户消息，仍执行工具循环。
- `runRaw()` 只执行一次模型请求，跳过 Session、PromptBuilder 和自动工具循环。
- 当前 `maxTurns` 与事件中的 `turn` 主要计数模型调用步骤，不等于 3.0 定义的用户交互轮。
- ListSession 通过生成边界将一次工具循环归入一个候选。

### 3.2 当前 Session 与 PromptBuilder 的访问

- Session 是必传参数，没有自动创建逻辑。
- PromptBuilder 可选，没有传入时保持 `undefined`。
- `agent.session` 和 `agent.promptBuilder` 返回持有的实例。
- 可以独立修改传入的实例，也可以用 `setPromptBuilder()` 替换或移除 Builder。
- 没有公开的 Session 替换接口。
- 现有 Message 可用 `setText()`、`setParts()` 编辑内容；直接改动 `parts` 需要注意缓存失效。
- TreeSession 的结构操作分散在 Message、Session、Inserter、Paginator 等对象中。
- ListSession 的多数结构修改操作在生成期间被禁止。
- Agent 有提交前 Hook，但上下文构建和请求发送阶段主要封装在私有方法中。

### 3.3 当前 PromptBuilder 的临时性与状态变化

主要代码见 [PromptBuilder.ts](../src/legacy/prompt/PromptBuilder.ts) 和 [Injection.ts](../src/legacy/prompt/Injection.ts)。

Agent 不会将 `build()` 产出的上下文整体写回 Session，注入消息通常只参与请求。

但是，构建只复制消息数组，历史里的 Message 对象仍然共享。自定义操作若直接修改这些 Message，会影响 Session 中的内容。临时数组并不意味着消息对象完全隔离。

每次模型调用都会重新构建上下文。注入生命周期按构建消耗，通过概率判定的注入即使没有匹配到位置也会消耗；手动 `build()` 预览也会改变生命周期状态。

### 3.4 当前继续与恢复

当前 `continue()` 最终调用 `run(继续提示)`，会保存用户提示并追加新的助手消息，不会合并原回复或删除提示。

`resume()` 调用严格恢复模式的 `continue()`，根据可恢复状态继续发起模型请求。当前 API 将普通继续与异常恢复放在同一套入口中，与拟定的 3.0 继续生成语义有差异。

### 3.5 当前工具审批、执行与 SDK 接入

- 审批请求、人工确认、待审批列表和审批超时主要实现在 Agent 中。
- [ToolKit](../src/legacy/tool/ToolKit.ts) 负责查找工具、解析参数、调用工具并返回工具结果消息。直接执行 ToolKit 不会经过 Agent 审批。
- 工具定义还有校验、执行前后、错误和序列化 Hook。
- 源码未直接导入模型厂商 SDK，但 [内置 Client](../src/legacy/client/ModelClient.ts) 主要通过传入的 SDK 形状对象发送请求。
- 当前 [ToolSchema](../src/legacy/tool/Tool.ts) 使用 OpenAI function tools 格式；独立于 SDK 还需要进一步独立于平台数据格式。

### 3.6 当前配置入口

模型请求参数的覆盖顺序是 `RequestConfig → Agent.requestOptions → 单次运行参数`。

单次运行参数中的 `signal`、`timeoutMs`、`stream`、`promptBuildOptions`、`serializeOptions` 被单独处理，其余字段视为模型请求参数。

审批、工具错误策略、最大模型调用次数、提示词注入、thinking 序列化等配置分布在不同模块。接口整理应明确每一类配置的归属，而不只是更换链式方法名称。

现有用法详见 [API 文档](./API.md)。

## 4. 待评估的设计建议

以下内容在讨论中提出，但尚未定为最终方案。

### 4.1 基础模型与公共会话接口

- 将 Turn 做成可复用的数据模型，供 ListSession 的 turn 模式和 AgentSession 使用。
- 区分 Turn（用户交互）、Step（模型步骤）、Run（一次执行及其控制状态）。恢复执行可关联原 Turn，Run 与 Turn 不必一一对应。
- 公共会话接口使用 `Session` 或 `SessionLike` 等名称。当前 `AgentSession` 是接口名，需要为新的具体会话类让出名称。
- 用公共会话契约和生成提交边界协调写入，减少 Agent 内部按具体类型分支，也允许用户实现自己的 Session。
- ListSession 的候选单位在创建时固定；模式转换采用显式操作，而非任意运行时切换。
- Session 提供方便的查询、结构删除和生成提交接口；内容编辑的便捷操作委托 Message，并感知内容变化以维护历史和索引。
- 2026-10-08 补充已确认所有 Session 保留轮次信息；具体身份、生成贡献、查询与提交方案见 [数据模型契约草案](./DATA-MODEL-3.0.md)。草案中的字段及默认策略不自动视为已确认。

### 4.2 Provider 的外部统一与内部拆分

- Provider 对外提供统一的完整响应和流式调用接口。
- 内部区分 HTTP 传输、请求与响应转换、流式协议解析；常规用户只需配置 Provider。
- 考虑按协议提供 OpenAI Compatible、OpenAI Responses、Anthropic 和 Gemini 实现。当前支持的 Chat Completions 与 Responses 不应被视为同一种协议。
- 常用生成参数统一，平台专属参数通过有类型的入口提供。
- 明确模型能力、不支持参数和冲突配置的处理，不静默忽略或统一钳制所有平台参数。
- 保留协议往返所必需的签名、推理状态等数据，避免统一 Message 时丢失多轮工具调用所需信息。

### 4.3 API、配置与扩展入口

- `chat()` 开始新交互；`continue()` 扩展已有回复；`resume()` 恢复执行。此前提出 Agent.generate 使用现有上下文，2026-10-08 用户进一步提出将一次生成下沉到小于 Agent 的独立单元，详见 4.4；最终入口归属待确认。
- 按模型生成、运行控制、工具执行、上下文构建划分有类型的配置，提供编辑器补全和最终生效配置查看能力。
- 提供请求前和提交前扩展入口，区分普通通知事件与会影响执行结果的异步 Hook。
- 提供不消耗生命周期的上下文预览，并明确注入按用户交互、模型步骤或请求次数生效的语义。
- 继续指令可只存在于临时上下文，从而实现最终不保留指令的行为。
- 生成开始时绑定提交目标；目标被编辑、删除或候选切换时，应有明确的结果归属和冲突处理规则。
- 工具执行入口可命名为 ToolExecutor，统一校验、授权、审批和执行；Agent 协调等待状态。具体拆分待定。

### 4.4 一次生成与 Agent 自主执行分别建模

2026-10-08 用户提出：Agent 应当是带上下文、能够多步自主运行的编排单元；调用方自行维护上下文与流程时，应使用一个小于 Agent 的生成单元。

用户随后认可这一组织方式。独立单次生成与 Agent 多步骤自主执行的职责拆分已确认；默认名称、入口和实现次序收敛到 [实施计划](./PLAN-3.0.md)。

现状说明：2.2.0 的 Agent.generate 并不只请求一次模型，它仅省略追加用户消息，仍运行完整工具循环。

讨论草案：

- 小单元暂称 Generator：接收明确的上下文、模型配置和可见工具定义，执行一次模型生成，输出统一响应及增量事件。
- 一次生成可以使用流式或完整响应，也可以返回工具调用；Generator 不自动执行工具、不追加工具结果、不再次请求模型。
- Generator 不拥有会话和自主循环。用户可以从自己的 Session、PromptBuilder 取得上下文，再调用它，并自行决定提交和后续动作。
- Agent 组合 Generator、Session、PromptBuilder 和工具执行模块，维护多步流程、执行记录与停止条件。
- Provider 保持平台协议与传输边界；Generator 提供独立、方便的单次生成入口，避免业务自定义流程必须先创建 Agent。
- Agent 侧的 generate 是否移除或保留一个含义明确的任务入口、小单元最终名称，以及与 Provider 的配置分工，尚未最终确定。
- 一次 chat 是一轮用户交互，可以包含多个模型 Step；带上下文的 Agent 可连续接受用户交互。不能将多步自主执行与多个用户交互混为一谈。

## 5. API 方向示例（非最终接口）

```ts
const session = ListSession.create({ candidateUnit: "sequence" });
const promptBuilder = new PromptBuilder();

const agent = new Agent({
  provider,
  model: "model-name",
  session,
  promptBuilder,
});

await agent.chat("帮我分析这个问题");
await agent.continue({ instruction: "继续展开第二点" });

// 不提供会话时，指定模式自动创建。
const anotherAgent = new Agent({
  provider,
  model: "model-name",
  mode: "agent",
});

anotherAgent.session;
anotherAgent.promptBuilder;
```

候选单位默认 sequence 已确定；`candidateUnit`、`mode`、`instruction` 等字段名称和上述构造签名仍是草案。
